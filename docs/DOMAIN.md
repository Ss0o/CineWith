# 도메인

## 1. 도메인 개요

영화 리뷰 및 추천 커뮤니티의 V1 핵심 도메인은 `Member`, `Movie`, `Review`, `Comment`다.

- `Member`는 Google OAuth2 인증만 완료한 사용자가 아니라 커뮤니티 닉네임 설정까지 마쳐 가입이 완료된 사용자를 의미한다.
- `Movie`는 TMDB 전체 영화의 복제본이 아니라 우리 서비스에서 리뷰 작성에 실제 사용된 영화를 의미한다.
- `Review`는 회원이 특정 영화에 작성한 평점 포함 콘텐츠다.
- `Comment`는 회원이 특정 리뷰에 작성한 단일 단계의 의견이다.

이 구조는 외부 영화 데이터와 커뮤니티가 소유하는 콘텐츠의 책임을 분리하고, V1에서 실제로 필요한 데이터와 규칙만 관리하기 위해 선택했다. 이 문서는 도메인 개념과 불변 조건을 정의하며 Java 클래스, DB 테이블, API 계약을 정의하지 않는다.

## 2. Member

`Member`는 커뮤니티 가입이 완료된 사용자다. 최초 OAuth2 인증 성공만으로는 `Member`가 되지 않으며, 커뮤니티에서 사용할 닉네임까지 설정해야 생성된다. 인증만 완료한 사용자를 불완전한 회원 상태로 저장하지 않기 때문에 V1에는 `PENDING`, `ACTIVE` 등의 회원 상태를 두지 않는다.

### 필드

| 필드 | 타입 | 의미 |
| --- | --- | --- |
| `id` | `Long` | 서비스 내부에서 사용하는 회원 식별자 |
| `provider` | `OAuthProvider` | OAuth2 인증 공급자 |
| `providerId` | `String` | 공급자가 부여한 사용자 식별자. Google의 경우 `sub` |
| `email` | `String` | OAuth2 공급자에서 받은 이메일 정보. 회원 식별자로 사용하지 않음 |
| `nickname` | `String` | 리뷰와 댓글에서 사용할 커뮤니티 닉네임 |
| `createdAt` | `Instant` | UTC 기준 가입 완료 절대 시각 |

### 규칙과 설계 이유

- OAuth2 사용자는 `provider + providerId` 조합으로 식별하며 이 조합은 중복될 수 없다. 공급자가 보장하는 사용자 식별자를 공급자 범위와 함께 사용해 이메일 변경이나 공급자 간 식별자 충돌의 영향을 피한다.
- Google OAuth2의 `providerId`는 Google의 `sub`를 의미한다.
- `nickname`은 중복될 수 없다. 커뮤니티에서 사용자를 구분할 수 있는 일관된 표시 이름을 제공하기 위함이다.
- `email`은 회원 식별자로 사용하지 않는다. 이메일은 변경될 수 있고 OAuth2 공급자의 고유 사용자 식별자를 대신하지 않기 때문이다.
- 최초 OAuth2 인증 성공 시 기존 `Member`가 없다면 OAuth 사용자 정보를 가입 진행 상태에서 임시로 유지한다. 사용자가 닉네임을 설정한 후에만 `Member`를 생성한다.
- V1에서는 회원 상태 필드를 추가하지 않는다. 미완료 가입을 영속 회원으로 표현하지 않아 상태 전이와 예외 상태를 불필요하게 늘리지 않기 위함이다.

## 3. Movie

`Movie`는 TMDB 검색 결과 전체를 저장하는 카탈로그가 아니라 우리 서비스에서 리뷰 작성에 사용된 영화의 최소 참조 정보다.

### 필드 후보

| 필드 | 타입 | 의미 |
| --- | --- | --- |
| `id` | `Long` | 서비스 DB에서 사용하는 영화 식별자 |
| `tmdbId` | `Long` | TMDB가 부여한 영화 식별자 |
| `title` | `String` | 영화 제목 |
| `posterPath` | `String` | TMDB 포스터 경로 |
| `releaseDate` | `LocalDate` | 영화 개봉일 |
| `createdAt` | `Instant` | UTC 기준 서비스 저장 절대 시각 |

### 규칙과 설계 이유

- 서비스 DB의 기본 식별자와 `tmdbId`를 분리한다. 내부 데이터 관계가 외부 공급자의 식별 체계에 직접 종속되는 것을 줄이기 위함이다.
- `tmdbId`는 중복될 수 없다. 같은 TMDB 영화를 서비스 내부에서 하나의 영화로 참조하기 위함이다.
- 영화 검색은 TMDB API를 이용하며, TMDB 전체 영화 데이터는 우리 DB에 저장하지 않는다. 외부 카탈로그를 불필요하게 복제하지 않고 데이터 소유권을 명확히 하기 위함이다.
- 사용자가 리뷰를 작성할 때 해당 `tmdbId`의 `Movie`가 없으면 저장한다. 실제 커뮤니티 콘텐츠가 참조하는 영화만 영속화하기 위함이다.
- V1에서는 `title`, `posterPath`, `releaseDate` 등 서비스에 필요한 최소 정보만 저장한다.
- `overview`, `runtime`, `cast` 등의 상세 정보는 현재 `Movie`에 저장하지 않는다. 검색과 상세 정보의 원천은 TMDB이며, 아직 필요성이 확정되지 않은 데이터를 내부 모델에 포함하지 않기 위함이다.

## 4. Review

`Review`는 한 회원이 한 영화에 대해 작성하는 평점 포함 콘텐츠다. 회원과 영화의 조합당 하나만 허용해 같은 작성자의 평가 단위를 명확하게 유지한다.

### 필드 후보

| 필드 | 타입 | 의미 |
| --- | --- | --- |
| `id` | `Long` | 리뷰 식별자 |
| `member` | `Member` | 리뷰 작성자 |
| `movie` | `Movie` | 리뷰 대상 영화 |
| `title` | `String` | 리뷰 제목 |
| `content` | `Text/String` | 리뷰 본문 |
| `rating` | `Integer` | 내부적으로 `1`부터 `10`까지 저장하는 평점 |
| `createdAt` | `Instant` | UTC 기준 리뷰 작성 절대 시각 |
| `updatedAt` | `Instant` | UTC 기준 리뷰 최종 수정 절대 시각 |

### 규칙과 설계 이유

- `Review`는 반드시 하나의 `Member`와 하나의 `Movie`에 속한다. 작성자와 평가 대상을 명확히 하기 위함이다.
- `member + movie` 조합은 중복될 수 없다. 한 회원이 같은 영화에 작성할 수 있는 리뷰를 하나로 제한하기 위함이다.
- 리뷰 작성자만 자신의 리뷰를 수정하거나 삭제할 수 있다. 콘텐츠 소유권을 작성자에게 한정하기 위함이다.
- `rating`은 내부적으로 `1`부터 `10`까지의 정수로 표현하고, 사용자에게는 `0.5`부터 `5.0`까지 `0.5` 단위 평점으로 표현한다. 부동소수점 오차 없이 사용자 표현 단위를 정확하게 보존하기 위함이다.
- V1에서는 영화 평균 평점을 별도 필드로 저장하지 않고 필요할 때 `Review` 데이터를 기반으로 계산한다. 동기화해야 할 파생 데이터를 만들지 않고 정확성과 단순성을 우선하기 위함이다.

## 5. Comment

`Comment`는 회원이 특정 리뷰에 작성하는 단일 단계의 콘텐츠다.

### 필드 후보

| 필드 | 타입 | 의미 |
| --- | --- | --- |
| `id` | `Long` | 댓글 식별자 |
| `member` | `Member` | 댓글 작성자 |
| `review` | `Review` | 댓글이 속한 리뷰 |
| `content` | `Text/String` | 댓글 내용 |
| `createdAt` | `Instant` | UTC 기준 댓글 작성 절대 시각 |
| `updatedAt` | `Instant` | UTC 기준 댓글 최종 수정 절대 시각 |

### 규칙과 설계 이유

- `Comment`는 반드시 하나의 `Review`와 하나의 `Member`에 속한다. 댓글의 문맥과 소유자를 명확히 하기 위함이다.
- 로그인한 `Member`만 댓글을 작성할 수 있다.
- 댓글 작성자만 자신의 댓글을 수정하거나 삭제할 수 있다. 리뷰 작성자는 다른 회원이 작성한 댓글을 삭제할 수 없다. 리뷰 소유권이 타인의 댓글 소유권까지 확장되지 않도록 하기 위함이다.
- V1에서 댓글 삭제는 Hard Delete로 처리한다. 복구, 감사, 모더레이션 요구사항이 없는 현재 범위에서 삭제 상태와 보존 정책을 추가하지 않기 위함이다.
- V1에서는 대댓글을 지원하지 않는다. 단순한 리뷰별 댓글 구조를 유지하기 위함이다.

## 6. 관계

| 시작 | 관계 | 대상 | 의미 |
| --- | --- | --- | --- |
| `Member` | 1:N | `Review` | 한 회원은 여러 영화에 리뷰를 작성할 수 있다. 각 리뷰의 작성자는 한 명이다. |
| `Member` | 1:N | `Comment` | 한 회원은 여러 댓글을 작성할 수 있다. 각 댓글의 작성자는 한 명이다. |
| `Movie` | 1:N | `Review` | 한 영화에는 여러 회원의 리뷰가 작성될 수 있다. 각 리뷰는 한 영화를 대상으로 한다. |
| `Review` | 1:N | `Comment` | 한 리뷰에는 여러 댓글이 작성될 수 있다. 각 댓글은 한 리뷰에 속한다. |

## 7. 도메인 불변 조건

- `Member`의 `provider + providerId` 조합은 유일하다.
- `Member`의 `nickname`은 유일하다.
- Google 회원의 `providerId`는 Google `sub`다.
- OAuth2 인증만 완료하고 닉네임 설정을 마치지 않은 사용자는 `Member`가 아니다.
- `Movie`의 `tmdbId`는 유일하다.
- `Review`는 작성자와 대상 영화 없이 존재할 수 없다.
- `Review`의 `member + movie` 조합은 유일하다.
- `Review.rating`은 `1`부터 `10`까지의 정수다.
- `Comment`는 작성자와 대상 리뷰 없이 존재할 수 없다.
- 리뷰와 댓글은 각각 자신의 작성자만 수정하거나 삭제할 수 있다.
- 리뷰 작성자라는 이유만으로 다른 회원의 댓글을 수정하거나 삭제할 수 없다.

이 조건들은 애플리케이션 계층의 검사에만 의존하지 않고 동시 요청에서도 깨지지 않도록 보장해야 한다. 구체적인 구현 및 DB 제약 방식은 이후 설계에서 결정한다.

### 저장 시간 기준

- 서버가 저장하는 `createdAt`, `updatedAt`의 기준은 UTC로 통일한다.
- 저장 시각은 서버나 개발자 장비의 기본 Local Timezone에 따라 달라져서는 안 된다.
- Java에서는 `Instant`, PostgreSQL에서는 `timestamp with time zone`(`timestamptz`)을 사용해 UTC 절대 시점을 표현한다.
- 생성·수정 시각을 부여하는 Clock 또는 Auditing 방식도 구현 단계에서 결정한다.

## 8. V1에서 의도적으로 제외한 설계

다음 항목은 현재 도메인 모델에 미리 추가하지 않는다.

- 좋아요
- 팔로우
- 대댓글
- 이미지 첨부
- 회원 탈퇴
- 관리자 및 모더레이션
- Redis
- Cache
- Fetch Join
- Cursor Pagination
- 성능을 위한 비정규화
- 영화 평균 평점 저장
- 리뷰 개수 저장
- `Member` 상태(`PENDING`, `ACTIVE` 등)

## 9. 추후 결정이 필요한 미결정 사항

- 가입 진행 중인 OAuth 사용자 정보를 어디에 어떤 수명으로 임시 유지할지
- 가입 진행 중 세션 만료, 닉네임 중복 요청, 가입 재시도 시 처리 방식
- 닉네임의 길이, 허용 문자, 변경 가능 여부
- 이메일의 필수 여부, 갱신 정책, 미제공 시 처리 방식
- 제목과 본문의 길이, 빈 값 허용 여부 등 리뷰 검증 규칙
- 댓글 길이와 빈 값 허용 여부 등 댓글 검증 규칙
- TMDB가 제목, 포스터 경로, 개봉일을 제공하지 않는 경우의 처리 방식
- 이미 저장된 영화의 최소 정보를 TMDB 변경에 맞춰 갱신할지 여부와 갱신 시점
- 리뷰 삭제 시 소속 댓글을 함께 Hard Delete할지 여부
- `createdAt`, `updatedAt`을 부여하고 갱신할 Clock 또는 Auditing 방식
- 도메인별 트랜잭션 및 Aggregate 경계
- 내부 식별자를 외부 API에 노출할지 여부
